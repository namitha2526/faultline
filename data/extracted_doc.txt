What is Faultline?
Faultline is a self-hosted production-grade error intelligence platform. A lightweight JS SDK captures errors from any app, ships them through a Kafka pipeline, and a Python ML service (CodeBERT + DBSCAN) groups them by actual root cause — not just stack trace hash. Smarter than Sentry. Costs Rs. 0 to build and run.
1. Problem Statement
Error monitoring tools like Sentry group errors by stack trace hash. This is fundamentally broken: the same logical bug produces dozens of different stack trace variants across browsers and OS versions. Engineers end up with 50 different error groups that are the same underlying bug.
Core pain points
Duplicate error groups — same bug, 50 different Sentry issues
No intelligent priority — a low-frequency error crashing premium users looks same as a harmless warning
Sentry ML grouping is paid ($26+/month). No session replay on free tier
No cross-service root cause analysis for microservice errors

5. ML Pipeline — The Core Innovation
The ML grouping service runs as a separate FastAPI microservice, called asynchronously from the Kafka consumer. It has three steps: embed, cluster, score.
Step 1 — Stack trace embedding (CodeBERT + MiniLM)
from sentence_transformers import SentenceTransformer
# Load once at service startup — runs on CPU, no GPU needed
model = SentenceTransformer("all-MiniLM-L6-v2")  # 90MB download once
def embed_stack_trace(stack_trace: str) -> list[float]:
cleaned = stack_trace.strip()[:2000]  # truncate to 512 tokens
embedding = model.encode(cleaned, normalize_embeddings=True)
return embedding.tolist()  # 384-dimensional vector
Step 2 — DBSCAN clustering
DBSCAN groups similar error embeddings without needing a fixed cluster count. Errors with cosine distance < 0.3 are grouped as the same root cause.
from sklearn.cluster import DBSCAN
import numpy as np
def cluster_errors(embeddings: list) -> list[int]:
db = DBSCAN(eps=0.3, min_samples=2, metric="cosine")
labels = db.fit_predict(np.array(embeddings))
# -1 means noise (unique error, no group yet)
return labels.tolist()
Step 3 — Impact scoring
Each error group is ranked by impact score, not just frequency. Critical bugs affecting paying users surface to the top.
def calculate_impact_score(group) -> float:
unique_users   = group['affected_user_count']
frequency      = group['occurrence_count']
session_ends   = group['sessions_ended_after_error']
total_sessions = group['total_sessions']
churn_rate = session_ends / max(total_sessions, 1)
# Weighted: users matter most, then frequency, then churn
impact = (unique_users * 0.4) + (frequency * 0.3) + (churn_rate * 100 * 0.3)
return round(impact, 2)
6. Database Schema
PostgreSQL — relational data
-- Projects
CREATE TABLE projects (
id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
name        VARCHAR(255) NOT NULL,
dsn         VARCHAR(255) UNIQUE NOT NULL,  -- SDK auth key
created_at  TIMESTAMPTZ DEFAULT NOW()
);
-- Error groups (one row per root cause cluster)
CREATE TABLE error_groups (
id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
project_id       UUID REFERENCES projects(id),
fingerprint      VARCHAR(64) UNIQUE NOT NULL,
title            TEXT NOT NULL,
culprit          TEXT,      -- decoded file:line from sourcemap
status           VARCHAR(20) DEFAULT 'unresolved',
impact_score     FLOAT DEFAULT 0,
affected_users   INT DEFAULT 0,
occurrence_count INT DEFAULT 0,
first_seen       TIMESTAMPTZ DEFAULT NOW(),
last_seen        TIMESTAMPTZ DEFAULT NOW()
);
-- Individual error events
CREATE TABLE error_events (
id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
group_id    UUID REFERENCES error_groups(id),
project_id  UUID REFERENCES projects(id),
message     TEXT NOT NULL,
stack_trace TEXT,
user_id     VARCHAR(255),
session_id  VARCHAR(255),
browser     JSONB,         -- { name, version, os }
embedding   FLOAT[],       -- 384-dim MiniLM vector
received_at TIMESTAMPTZ DEFAULT NOW()
);
-- rrweb session replay chunks
CREATE TABLE replay_events (
id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
session_id VARCHAR(255) NOT NULL,
project_id UUID REFERENCES projects(id),
events     JSONB NOT NULL,  -- serialised DOM mutation events
timestamp  TIMESTAMPTZ DEFAULT NOW()
);
ClickHouse — time-series error metrics
CREATE TABLE error_metrics (
project_id   String,
group_id     String,
timestamp    DateTime,
error_count  UInt32,
user_count   UInt32,
environment  String
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(timestamp)
ORDER BY (project_id, group_id, timestamp);
-- Materialised view for fast hourly charts
CREATE MATERIALIZED VIEW error_metrics_hourly AS
SELECT project_id, group_id,
toStartOfHour(timestamp) AS hour,
sum(error_count) AS total_errors
FROM error_metrics GROUP BY project_id, group_id, hour;

13. Interview Talking Points
Use these answers when interviewers ask about the project in technical rounds.
System design questions
Why Kafka? — Decouples ingestion from ML processing. Ingestion API never blocks on model inference. Handles traffic spikes without losing events. Replay-able on failure.
Why ClickHouse over PostgreSQL for errors? — ClickHouse is columnar storage. Time-range queries on 10M rows finish in 200ms vs 8+ seconds in PostgreSQL.
How did you handle backpressure? — Kafka consumer group lag monitoring. If ML service falls behind, scale consumer replicas horizontally with Docker Compose.
How did you prevent duplicate errors? — Idempotency key: MD5(project_id + stack_trace_hash + 60s_time_bucket). Redis SET NX with TTL rejects duplicates.
ML questions
Why DBSCAN over k-means? — k-means needs a fixed cluster count. We never know how many distinct error types a project has. DBSCAN finds them automatically and marks outliers as noise (label -1).
Why CodeBERT over generic BERT? — CodeBERT is pre-trained on GitHub code + docstrings. It understands function names, file paths, and code patterns in stack traces better than general-purpose text models.
Cold start problem? — First 10 errors use exact hash fingerprinting. Once 10+ errors exist, DBSCAN runs and reassigns. Groups can merge as more data accumulates.
Frontend questions
How does session replay work? — rrweb records serialised DOM mutations as JSON events. On replay, it re-applies mutations in order on a shadow DOM. No screenshots — just efficient DOM diffs.
How do you link replay to an error? — Each error event carries a session_id and timestamp. Replay player scrubs to that exact timestamp and highlights the DOM state at the moment of crash.
